Let AI agents near money without trusting the model

TellerGate is an authorization gateway that sits between a bank's AI agents and the systems they can touch. Every tool call is allowed, denied or held for a person by rules the bank wrote, and every decision goes into a signed audit log. A prompt-injected model cannot talk its way past it.

Assume the model is compromised. Make that not matter.

Bank agents read untrusted text all day: customer emails, uploaded documents, web pages. Any of it can carry instructions aimed at the model, and today's models cannot reliably tell the bank's instructions from an attacker's. Classifiers and careful prompts help, but they are probabilistic, and in banking one success is enough.

TellerGate lets the model propose actions. Whether an action happens is decided by three things, none of which depend on the model behaving well:

Rules

Written by the bank. This agent may pay registered payees, up to a threshold, with these argument formats and no others.

Facts

About the session. This agent read an untrusted email in this conversation, and this account number was copied out of that email.

People

With names. Maria approved this exact payment; two different people approved the large one; Priya, the named overseer, halted the agent.

How it works

It speaks the Model Context Protocol natively, so it drops in front of existing MCP tool servers without code changes. Agent frameworks that do not use MCP call a plain HTTP decision API instead.

ALLOWHOLD FOR A PERSONDENY
→
Bank systemsPayments, mailbox and ledger tool servers, reachable only through the gateway
  1. The agent sends a tool call with its own token. Its identity comes from the token; the request body cannot claim to be another agent.
  2. The engine runs nine checks in a fixed order and produces a decision with a list of reasons. No model is consulted.
  3. The decision is appended to the signed audit log first. If the write fails, the call is denied.
  4. Allowed calls are forwarded. The response comes back through TellerGate, which masks card numbers and marks the session as tainted if the tool is an untrusted source.
  5. Held calls wait for people. The approval is bound to a hash of the exact call, is single-use and expires. Denials come back with reasons the model can explain to the user.

The nine checks

The first hard failure denies. Softer findings accumulate and send the call to a person. If nothing escalates, the decision is ALLOW with the reason all-rules-passed.

1Kill switchAgent, or all agents, halted by a named overseerDeny before anything else
2Identity and scopeUnknown agent, unknown tool, tool not granted to this agentDeny by default
3Rate limitRunaway loops, injected "repeat this 500 times"Deny
4Argument schemaUnknown or missing arguments, wrong types, out-of-range numbers, overlong strings, pattern mismatchesDeny
5AllowlistsDestination not on a human-maintained list, such as registered payeesConfigurable: deny or hold
6TaintThe session has read untrusted contentHold by default for high and critical tools
7ProvenanceAn argument appears in untrusted content the agent read, such as the attacker's account number lifted from the emailDeny by default for critical tools
8Amount thresholdsAbove the single-approval threshold, or above the dual-control thresholdHold for one, or two different, approvers
9Advisory detectorsInjection phrasing or hidden characters inside the argumentsCan escalate to a person; never allows

The agent proposes. The bank decides.

These guarantees come from policy, identity and cryptography, not from a model's judgement.

TellerGate includes heuristic injection detectors, but they are advisory: they can send a call to a person, never allow one.

  • Default deny. Agents only see and call the tools they are granted; others are hidden from tools/list.
  • Maker-checker. The agent makes, a named person checks. Approving a 2,400 payment does not authorize 24,000 or a different payee.
  • Dual control. Above a threshold, two different people must approve. The same person twice is rejected.
  • Agents cannot approve. Agent tokens are refused on the admin API outright.
  • Named overseers. Only people listed in the policy can halt an agent. TellerGate will not start without one.
  • Signed audit trail. Each record is hash-chained and Ed25519-signed. Auditors verify it with the public key alone.
  • Card numbers masked. Tool output is scanned and card numbers reduced to first six and last four before the model sees them.
  • Standard library only. No third-party Go modules, which keeps the supply chain auditable.

Answers for examiners and model risk teams

Reporting on US bank examinations describes examiners asking how AI is stopped, who is accountable, and whether it can reach systems it was not authorized to use. TellerGate gives each question a concrete answer. This mapping shows where TellerGate produces evidence; it is not a claim of compliance with any framework.

QuestionEvidence TellerGate produces
How do you stop the AI, and who is accountable?Kill switch limited to overseers named in the policy; every halt and release signed into the log with name, time and reason
Can the AI reach systems it was not authorized to use?Per-agent tool grants, enforced and logged; ungranted tools hidden from the agent
Is there a human in the loop for material decisions?Thresholds, maker-checker and dual control, with approver identities in the log
Can you explain why the AI did, or did not, do something?Every decision lists the deterministic rules that produced it
Is the record trustworthy?Signed hash chain, verifiable independently with a public key
How do you govern third-party AI vendors?The gateway works the same in front of any model or agent vendor

It also addresses five of the OWASP Top 10 risks for LLM applications (2025): prompt injection, sensitive information disclosure, improper output handling, excessive agency and unbounded consumption.

Install in three steps

Needs Go 1.24 or later. No API keys, no network and no language model. The full guide is the README in the repository.

  1. Get the source and run the demo

    The source is shared on request while TellerGate is in pilot.

    git clone https://github.com/AravindB98/tellergate.git
cd tellergate
make demo

  2. Build, keys and policy

    Create a signing key, issue a token per agent and per person, and check your policy.

    make build
./build/tellergate keygen -out keys/audit.key
./build/tellergate token -kind agent
./build/tellergate check -policy configs/policy.json

  3. Run and point an agent at it

    Give your MCP client the gateway's address instead of the tool server's, with the agent's token.

    ./build/tellergate serve -addr :8443 \
  -policy configs/policy.json \
  -principals configs/principals.json \
  -upstream https://payments-mcp.internal/mcp \
  -audit audit.jsonl -audit-key keys/audit.key \
  -tls-cert keys/tls.crt -tls-key keys/tls.key

Prefer containers? docker build -t tellergate . builds a distroless image that runs as non-root. Check the trail any time with ./build/tellergate verify -audit audit.jsonl -pub keys/audit.key.pub.

Before you rely on it

  • TellerGate has not been through an independent security review and is not certified for any regulatory regime. Commission a review before it handles real funds.
  • The shipped principals.json holds demo tokens ending in NOT_FOR_PRODUCTION. Replace every one.
  • Taint, approvals and halts are kept in memory per instance in 0.1. Run a single instance until shared state arrives in 0.2.
  • Upstream tool servers must accept traffic only from TellerGate. That is network policy, which TellerGate does not enforce by itself.
